# styles 目录设计说明

本目录是全站样式的「地基」：设计 token 与全局重置。本文说明每个设计决策背后的原因，以及它解决的问题。

## 目录分工

| 文件         | 职责       | 说明                                             |
| ------------ | ---------- | ------------------------------------------------ |
| `vars.scss`  | 设计 token | 颜色、边框、字号、过渡等全部设计变量的唯一定义处 |
| `reset.scss` | 全局重置   | 统一浏览器默认样式里与设计体系冲突的部分         |
| `index.scss` | 聚合入口   | 汇总上面两个文件，供应用一次性引入               |

另外 `tokens.ts`（token 目录的 TS 投影，见「四、使用约定」第 5 条）与 `__tests__/tokens.spec.ts`（防漂移测试）同在本目录。

## 一、设计 token（vars.scss）

### 1. 为什么用 CSS 自定义属性（`--el-*`）承载 token，而不是 SCSS 变量

SCSS 变量在编译后**消失**，只能做编译期替换；CSS 自定义属性编译后**仍然存在**，具备 SCSS 变量没有的能力：

- **运行时可变**：在运行时覆盖 `:root` 里的变量即可切换主题（品牌色定制、暗色模式），无需重新编译
- **局部覆盖**：某个组件可以在自身作用域内覆盖 token，只影响该组件子树
- **继承机制**：子元素自动继承，天然适合「全局定义、按需覆盖」的消费方式

因此两者各司其职：**SCSS 变量 + `mix()` + 循环负责「生成」token（编译期计算），CSS 变量负责「消费」token（运行期引用）**。

### 2. 为什么用 `$colors` map + 循环生成色阶，而不是手写每一条变量

5 个语义色 × 8 个变体 ≈ 40 条变量。手写的问题：

- 重复且容易漏写、抄错
- 每个变体都要手工调色，同色系深浅容易不统一

用 map + `@each`/`@for` 生成后：

- 新增/删除一个颜色只需改 map 一行，全部变体自动跟随
- 所有颜色遵循**同一条亮度公式**（与白色按百分比混合），不存在手调偏差

### 3. 为什么色阶是 light-3/5/7/9 + light-8 + dark-2 这六档

命名规则：`light-N` = 与白色混合 N×10%，`dark-N` = 与黑色混合 N×10%。

- **对齐 Element UI 2.x 官方色阶**：官方组件实际只用 light-3/5/7/9、light-8、dark-2 这六档（light-3 悬停、light-8 背景、dark-2 按压等），其余档位官方并未使用
- **不生成死代码**：官方未使用的档位不生成，避免输出一堆没人引用的变量
- **解决了「深浅没有档位可选」的问题**：没有色阶时，开发者需要「再浅一点」只能自己拍脑袋调色，导致同一个主色在不同组件里深浅不一；有了固定档位，组件之间天然一致

### 4. 为什么前缀选 `--el`

- 与 **Element Plus 官方 CSS 变量完全同名**：对照官方文档开发组件时可直接照抄变量名，迁移官方示例样式几乎零成本
- 与组件里 `$el-*` 的 SCSS 变量命名保持一致（历史沿革：早期从教程拷贝的 `--duyi` 前缀已统一改为 `--el`）

### 5. 为什么中性色按 text/border/fill 分组且每组分多档

组件的「灰阶」需求远超「一种灰色」：主文字、次要文字、占位文字、禁用文字深浅各异。分组 + 分档：

- 语义化分组让「选哪个灰」有明确依据（文字用 text 组、描边用 border 组、填充用 fill 组），而不是在色板里随机挑
- 分档（primary/regular/secondary/placeholder/disabled 等）覆盖全部灰阶场景，**避免组件里出现手写灰色**

### 6. 为什么定义复合 token（`--el-border`、`--el-disabled-*`、`--el-transition-*`）

- `--el-border` 聚合宽度/线型/颜色三要素：组件写一条 `var()` 即可完成描边；将来调整描边规范（如宽度改 2px）只动一处
- `--el-disabled-*` 语义化禁用态三件套（背景/文字/边框）：保证全站禁用态观感统一，而不是每个组件各自决定「禁用长什么样」
- `--el-transition-*` 统一动效时长：交互节奏全局一致，避免每个组件用不同的 duration 导致手感参差

## 二、样式重置（reset.scss）

### 1. 为什么是「轻量 reset」，而不是 normalize 或 `* { margin: 0 }`

三种路线：

| 路线                     | 做法                          | 问题                                                |
| ------------------------ | ----------------------------- | --------------------------------------------------- |
| 通配符清零               | `* { margin: 0; padding: 0 }` | 误杀第三方内容/富文本的默认观感，之后还得逐个补回来 |
| normalize.css            | 保留所有默认样式              | 与设计体系冲突的部分仍需再覆盖一遍，等于做了两层    |
| **轻量 reset（本方案）** | 只重置与设计体系冲突的部分    | —                                                   |

轻量 reset 的思路：**只统一排版、链接、标题、分隔线这几类与设计直接相关、且浏览器默认值千差万别的样式；组件间距由组件自身控制**。解决的问题：

- 不同浏览器默认样式差异导致的观感不一致
- 组件布局不被浏览器默认样式干扰，组件作者无需在每个组件里写补偿代码

### 2. body 排版基准为什么全部走 token

字体、字号、字色是全局排版的三要素，直接引用 `vars.scss` 的 token：**调整主题（如整体字号 +2px、换字体）只改一处**，无需翻遍所有组件。

另外清零 body 默认的 8px 外边距：浏览器默认留白会让全屏布局（顶栏、侧栏贴边）四周错位。

配套的两个渲染细节：

- `-webkit-font-smoothing: antialiased`：macOS 下默认渲染偏虚，细字体观感差
- `-webkit-tap-highlight-color: transparent`：移动端点按链接默认出现灰色高亮块，破坏组件视觉

### 3. 链接三态为什么用「颜色深浅」而不是「hover 下划线」

- 状态层级用深浅表达：默认主色 → 悬停 light-3（浅、柔和）→ 按压 dark-2（深、符合按压变深的物理直觉）
- 下划线方案的问题：浏览器默认 hover 下划线各网站表现不一，且与组件内链接（按钮、导航）冲突；统一为色彩反馈后，导航、组件内链接无需各自处理

### 4. 标题字号为什么用 `calc(基础字号 + Npx)` 而不是固定值

h1~h3 的字号以 `--el-font-size-base` 为基准递增（+6/+4/+2）：

- 标题与正文**保持固定比例关系**，产品要求整体放大/缩小字号时，只改 base 一个值，比例不变
- 手写 `h1 { font-size: 24px }` 这类固定值的问题：一旦调整正文字号，标题与正文的比例失衡，需逐一重调

### 5. 为什么清掉首/末元素的外边距

标题和段落默认携带上下外边距，放进卡片、弹窗等带 padding 的容器时，外边距 + 内边距叠加会**撑破留白设计**。

全局用 `:first-child` / `:last-child` 清掉后：

- 容器只需管自己的 padding，不再出现「h2 顶到哪儿」的不可预期问题
- 组件作者不必再写 `h2:first-child { margin-top: 0 }` 之类的补偿代码

### 6. 正文行高 1.8、hr 用边框画线

- `line-height: 1.8`：中文长段落的舒适阅读行高区间
- `hr` 重置为纯分割线：浏览器默认 hr 是带立体感的粗线，与扁平设计体系冲突；清掉默认边框后改用 token 色画一条顶部细线，颜色跟随主题

## 三、设计难点与亮点

前两节回答「做了什么、为什么」，本节聚焦几个技术上一眼看不透的决策点。

### 1. 色阶生成管线：40+ 条 token 零手写

`vars.scss` 用嵌套循环把「5 个语义色 × 8 个变体」的 token 全部交给编译期生成：

```scss
@each $val, $color in $colors {
  // 层一：遍历语义色
  --el-color-#{$val}: #{$color}; // 基准色
  @for $i from 1 through 4 {
    // 层二：公式覆盖的档位
    --el-color-#{$val}-light-#{2 * $i + 1}: ...;
  }
  --el-color-#{$val}-light-8: ...; // 层三：公式外的例外档位
  --el-color-#{$val}-dark-2: ...;
}
```

四个不显然的难点：

- **动态变量名靠插值拼出**：`#{$val}` 与 `#{2 * $i + 1}` 把变量名当作字符串拼接——SCSS 变量名带连字符（`--el-color-primary-light-3`），无法用普通循环变量表达，插值是唯一解法
- **`color.mix()` 的权重方向**：第三个参数是**第一个颜色**的占比。light 档第一个参数必须是白、dark 档必须是黑——方向写反整个色阶深浅颠倒，且产物「看起来也像那么回事」，是隐蔽的坑
- **公式与例外**：3/5/7/9 可由 `2i + 1` 一个公式覆盖；官方实际高频使用的 light-8 与 dark-2 不在公式内，单独生成。刻意**不生成** light-1/2/4/6 等官方未使用的档位，避免死代码
- **`* 1%` 显式单位**：`(2 * $i + 1) * 10 * 1%` 把无单位数显式转为百分比，消除传给 `mix()` 时的单位歧义
- **小数通道需取整**：Dart Sass 1.79 起 `color.mix()` 保留小数通道，直接输出会变成 `rgb(47.57%, 73.37%, 100%)` 百分比格式；`round-color()` 把通道四舍五入回整数，token 恢复 `#79bbff` 十六进制书写（取整后与官方色值完全一致，渲染无差异）

解决的问题：新增语义色只改 map 一行，全部变体按同一亮度公式自动产出——手工维护 40 条变量时必然出现的漏写、抄错、同色系深浅不一全部消除。

### 2. 编译期与运行期的边界：SCSS 变量生成、CSS 变量消费

两种变量各有一个不可跨越的限制，决定了 token 体系的管线方向：

- CSS 自定义属性**编译期不可读**：`var()` 的值要等浏览器运行时才确定，Sass 无法把 `var(--el-color-primary)` 交给 `color.mix()` 做计算——所以「生成」必须用 SCSS 变量完成
- SCSS 变量**运行期不存在**：编译后被替换成字面量，无法作为运行时换主题（暗色模式、品牌定制）的入口——所以「消费」必须用 CSS 变量完成

于是管线只能单向：`$colors map →（编译期）循环 + color.mix → --el-* 自定义属性 →（运行期）组件 var() 消费`。

解决的问题：同时拿到两边的能力——生成端享受编译期批量计算的效率与一致性，消费端保留运行时覆盖主题的灵活性；`$colors` 只在生成端出现一次，消费方永远只见 `--el-*`。

### 3. 复合 token：把「规范」编码进变量

- `--el-border` 聚合宽度/线型/颜色三要素：组件写一条 `var()` 完成描边，改描边规范全站一处生效
- `--el-disabled-*` 语义化禁用态三件套（背景/文字/边框）：防止每个组件各写一套禁用样式
- `--el-transition-*` 统一动效时长：交互节奏全局一致

难点在聚合粒度：过细（每个组件一套组合）失去统一性，过粗（一个万能变量包打天下）失去语义。这里的粒度标准是「**全站一致的规范**」——凡是需要全站一致的组合，就应聚合成一条 token。

### 4. 轻量 reset 的克制：难点在决定「不做什么」

重置样式的难点不在「清了什么」，而在「忍住没清什么」（取舍依据见二、1）：

- 不碰 `* { margin: 0 }`：通配符清零会抹掉富文本、表单、第三方组件的默认间距，事后逐项补回的代价大于清零省下的
- 只清「首末元素」的外边距：用 `:first-child` / `:last-child` 定点清掉标题、段落在容器边缘的默认外边距，既保住正文排版，又解决卡片/弹窗被撑破的问题
- 组件间距归组件：reset 只统一「浏览器默认值与设计体系冲突」的部分，间距决策权留给组件自身的 padding/margin

解决的问题：跨浏览器观感一致、组件布局可控，同时第三方内容与富文本保留浏览器默认观感。

## 四、使用约定

1. 组件样式一律通过 `var(--el-*)` 消费设计 token，**禁止手写 Element 色值**（`#409eff` 这类十六进制只允许出现在 vars.scss）
2. 需要新颜色时：语义色进 `$colors` map，灰阶进中性色分组，再由组件引用——不要绕过 token 直接在组件里写色值
3. 新增 token 命名遵循 `--el-<分组>-<语义>`（分组参考 color/text/border/fill/bg），与 Element Plus 官方命名对齐
4. **边界**：设计 token 用 CSS 变量（`--el-*`，运行时可变）；组件私有、编译期即可确定的值用 SCSS 变量（`$` 前缀）——不要混用
5. **目录投影的同步责任**：浏览器无法枚举自定义属性，色板类组件通过 `styles/tokens.ts` 消费 token 目录；改动 vars.scss 的变量名时，`styles/__tests__/tokens.spec.ts` 防漂移测试会拦截
